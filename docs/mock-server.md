# 모의 서버

백엔드 API가 준비되기 전에도 프론트엔드를 끝까지 동작시켜 보기 위한 가짜 백엔드다. Vite 개발 서버 안에서 실제 HTTP와 WebSocket으로 응답하므로, 프론트엔드 코드는 실제 백엔드에 붙을 때와 똑같다. 응답 형식은 [`설계/2_API명세서.md`](../설계/2_API명세서.md)를 따른다.

## 켜고 끄기

| 상황 | 방법 | 결과 |
|---|---|---|
| 모의 서버로 개발 | `npm run dev` (아무 설정 없이) | `/api/v1`을 모의 서버가 응답. 화면 오른쪽 아래에 "모의 서버" 조작판이 보인다 |
| 빌드 결과 확인 | `npm run build` 뒤 `npm run preview` | 미리보기 서버에서도 모의 서버가 동작 |
| 실제 백엔드에 연결 | `.env.local`에 `API_TARGET=http://localhost:8003` | 모의 서버가 꺼지고 Vite proxy(개발 서버가 요청을 다른 서버로 넘겨주는 기능)가 `/api`를 그 주소로 넘긴다. WebSocket도 넘긴다(`ws: true`). 조작판은 보이지 않는다 |
| 토큰 재발급 검수 | `.env.local`에 `MOCK_ACCESS_TTL_SEC=30` | 액세스 토큰이 30초 뒤 만료된다. 기본은 명세대로 3600초 |

- 환경 변수의 예시는 저장소 루트의 `.env.example`에 있다. 바꾼 뒤에는 개발 서버를 다시 띄운다.
- 전역 상수 `__MOCK_API__`가 모의 서버 여부를 알려 준다(`vite.config.ts`의 `define`). `App.tsx`는 이 값이 `true`일 때만 조작판(`MockPanel`)을 그린다.
- 데이터는 메모리에 두고, 바뀌면 0.25초 뒤 `node_modules/.cache/youthgarten-mock/db.json`에 기록한다. 개발 서버를 다시 띄워도 이어진다. 파일이 없거나 형식이 맞지 않으면 시드 데이터로 다시 시작한다. 처음부터 다시 하려면 조작판의 "데이터 초기화"를 누르거나 이 파일을 지운다.
- 일반 요청은 150~400ms, AI 대화는 1~2.5초 늦게 응답한다. 실제 네트워크처럼 기다리는 화면을 볼 수 있게 하기 위해서다.

- 민재의 시험은 시드를 만든 시각(처음 띄운 때나 "데이터 초기화"를 누른 때)에 남은 시간이 18분이다. 저장된 데이터로 다시 띄우면 그 시각부터 시간이 흐른 상태라, 오래 지났으면 자동 제출되어 있다. 처음 상태를 보려면 초기화한다.

## 검수용 API

명세에 없는 API는 모두 `/api/v1/__mock__/` 아래에 있다. 조작판이 이 API를 부른다. 🔒는 로그인한 사용자 기준으로 동작하며 `Authorization: Bearer` 헤더가 필요하다.

| 메서드 | 경로 | 인증 | 하는 일 | 요청 본문 |
|---|---|---|---|---|
| GET | `/__mock__/accounts` | | 시드 계정 목록과 현재 레벨, 공통 비밀번호 | |
| POST | `/__mock__/reset` | | 데이터를 시드로 초기화. 이전 토큰은 모두 무효가 되고 WebSocket 연결은 1012로 끊긴다 | |
| GET | `/__mock__/state` | 🔒 | 현재 계정, 지정해 둔 다음 채점 결과(`next_grade`, `next_grade_reason`), AI 실패 대기 여부, 진행 중인 시험 | |
| POST | `/__mock__/lectures/{id}/complete` | 🔒 | 강의 하나를 수강 완료(100%)로 처리 | |
| POST | `/__mock__/attempts/current/remaining` | 🔒 | 진행 중인 시험의 남은 시간을 지정한 초로 변경. 음수면 마감이 그만큼 지난 상태 | `{"remaining_sec": 60}` |
| POST | `/__mock__/next-grade` | 🔒 | 다음 채점 결과를 강제로 지정. `null`이면 해제. `fail`이면 미달의 종류(`reason`)를 고를 수 있다 | `{"result": "pass" \| "fail" \| "error" \| null, "reason"?: "task_score" \| "required_check" \| "ai_score" \| "verify_min"}` |
| POST | `/__mock__/next-ai-failure` | 🔒 | 다음 AI 답변을 한 번 `AI_UNAVAILABLE`(502)로 실패시킴 | 없음, 또는 `{"enabled": false}`로 해제 |
| POST | `/__mock__/expire-token` | 🔒 | 요청에 쓴 액세스 토큰을 즉시 만료시킴. 다음 요청은 401 `TOKEN_EXPIRED` | |

- "마감 + 1분 지남"으로 자동 제출을 검수하려면 남은 시간을 `-61`초로 바꾼 뒤 시험관에게 말을 건다(`GET /attempts/current`). 서버는 이때 자동 제출한다.
- 열려 있는 시험 화면의 타이머는 시험을 시작하거나 이어 풀 때 받은 `remaining_sec`로 돈다. 남은 시간을 바꾼 뒤에는 시험 화면을 다시 열어야 반영된다.
- 지정한 결과는 응시의 채점 기준(스냅샷)에 따라 다르게 맞춘다.

| 지정 | 두 영역 기준 (`DUAL_V1`) | 예전 기준 (`LEGACY_TOTAL_V1`) |
|---|---|---|
| `pass` | 규칙 점수가 이미 통과면 그대로. 아니면 결과물·답변 검증·AI 활용 역량을 최소 점수보다 조금 높게 올리고 필수 요건을 충족으로 바꾼다 | 이미 80점 이상이면 그대로, 아니면 82~90점 |
| `fail` (`reason` 없음) | 규칙 점수가 이미 미달이면 그대로. 아니면 두 영역의 점수를 모두 최소 점수 아래로 낮춘다 | 이미 80점 미만이면 그대로, 아니면 58~72점 |
| `fail` + `task_score` | 먼저 통과하는 점수로 맞춘 뒤 결과물만 최소 점수 아래로 (실무 과제 해결 점수 미달) | `reason`은 쓰지 않는다 |
| `fail` + `required_check` | 통과하는 점수에서 첫 번째 필수 요건만 미충족으로 (점수는 높은데 미통과) | |
| `fail` + `ai_score` | 통과하는 점수에서 질문 설계와 개선 과정을 낮춰 AI 활용 역량 점수만 미달 (답변 검증은 최소 점수 이상) | |
| `fail` + `verify_min` | 통과하는 점수에서 답변 검증만 검증 최소 점수 − 1점으로, AI 활용 역량 점수는 최소 점수 이상 (총점은 80점을 넘는데 미통과) | |

- 지정 때문에 바뀐 필수 요건 판정과 답변 검증 피드백에는 "(검수용 지정 결과)"라고 적는다. 실제 답안의 판정과 다르다는 것을 결과 화면에서 알 수 있게 하기 위해서다.
- 지정 때문에 답변 검증이 0점에서 양수가 되면, 근거 대화로 마지막 질문을 붙인다. AI와 나눈 대화가 하나도 없으면 근거 없이 둔다(이 경우만 아래 "근거 규칙"의 예외).
- `reason`은 `result`가 `fail`일 때만 받는다. 다른 값과 함께 보내면 422다. 기존 호출(`{"result": "fail"}`)은 그대로 동작한다.

## 모의 AI

질문의 낱말과 과제의 제공 자료로 답을 고른다. 같은 대화에는 늘 같은 답을 준다.

| 질문에 들어 있는 말 | 답 |
|---|---|
| 번역, 우리말로 | 주요 자료의 우리말 번역 |
| 검토, 고쳐, 피드백 + 답안, 내가 쓴 | 지금 저장된 답안에서 과제의 핵심 요소가 담겼는지 짚어 줌 |
| 정중, 어조, 톤 | 어조를 다듬는 예시 문장 |
| 써 줘, 작성해, 초안, 만들어 | 과제의 결과물 초안 (메일, 견적서, 검토 메모, 오류 목록, 정리표) |
| 요약, 정리, 파악, 알려 | 자료 요약 |
| 과제별 사실 낱말 (일정, 단가, 중량, 기한 등) | 그 사실 하나 |
| 수정해, 보완해, 구체적으로 | 반영한 초안을 다시 줌 |
| 그 밖 | 도울 수 있는 일과 과제 요령 하나. 질문이 짧으면 상황과 형식을 알려 달라고 덧붙임 |

### 일부러 섞는 틀린 사실

평가 항목 "답변 검증"이 의미를 갖도록, 과제마다 **첫 내용 답변(요약, 초안, 사실)에 자료와 다른 사실을 하나 섞는다.** 사용자가 지적하기 전까지는 계속 같은 틀린 값을 쓴다. 사용자가 그 주제를 짚어 "틀린, 다른, 맞는지, 확인해, 대조, 근거" 같은 말로 묻거나, 올바른 값을 직접 말하면 사과하고 바로잡는다.

| 과제 | AI가 틀리게 말하는 것 | 자료의 값 |
|---|---|---|
| 1. 납기 지연 항의 메일 회신 | 새 일정 11월 21일 출항, 12월 6일 도착 (바이어 기한을 못 맞춘다고 말함) | 11월 17일 출항, 12월 1일 도착 (선적 일정표) |
| 2. 견적서 작성 | DL-200 수량 할인 10%, 단가 USD 10.80 | 5%, USD 11.40 (단가표) |
| 3. 신용장 조건 검토 | 최종 선적일(44C) 12월 25일이라 문제없음 | 12월 5일, 선적 계획과 맞지 않음 (신용장 사본) |
| 4. 선적 서류 대조 | 총중량이 세 서류 모두 6,420kg으로 일치 | B/L 초안만 6,240kg (선하증권 초안) |
| 5. 수출 통관 절차 정리 | 수출신고 수리 뒤 60일 안에 선적 | 30일 (사내 안내 자료) |

- 틀린 사실을 말하기 전에 사용자가 먼저 "자료와 대조해 줘"처럼 검증을 부탁하면 처음부터 올바른 값을 준다.
- 자료 속 회사, 사람, 숫자는 모두 지어낸 것이다. 과제 5의 통관 절차는 일반적인 흐름을 요약한 교육용 내용이며, 실제 규정과 같은지는 확인 필요.

## 모의 채점

제출하면 4~6초 뒤에 결과를 저장한다. 채점은 응시를 만들 때 복사한 채점 기준(`grading_rubric_snapshot`)으로 한다. 과제마다 기준은 `mock/content.ts`의 `rubric`에 있고, 다섯 과제 모두 명세의 MVP 값(결과물 50, 질문 설계 15, 답변 검증 20, 개선 과정 15점, 실무 과제 해결 최소 40점, AI 활용 역량 최소 40점, 답변 검증 최소 12점)을 쓴다.

통과는 명세 9절의 식으로 서버가 계산한다(`mock/grader.ts`의 `decide`).

```text
실무 과제 해결 충족 = 결과물 ≥ 40 AND 필수 요건을 모두 충족
AI 활용 역량 충족   = (질문 설계 + 답변 검증 + 개선 과정) ≥ 40 AND 답변 검증 ≥ 12
통과               = 두 영역 모두 충족
```

| 항목 | 점수를 매기는 근거 (25점 기준으로 센 뒤 배점에 맞춰 늘이거나 줄인다) | 근거 대화(`evidence_message_id`) |
|---|---|---|
| 결과물 | 답안 길이(최대 10점) + 과제의 핵심 요소를 담은 비율(최대 15점). AI가 섞은 틀린 값이 답안에 남아 있으면 6점 뺌 | 없음 |
| 질문 설계 | 질문 하나에 담긴 역할·상황·조건·형식의 최대 개수 × 4.5점 + 다른 질문에서 더 쓴 요소, 질문 평균 길이(최대 5점), 질문 수(최대 3점) | 요소를 가장 많이 담은 질문 |
| 답변 검증 | 아래 표. 배점 대비 비율로 매긴다 | 학습자의 질문만 (AI 답변은 근거로 쓰지 않는다) |
| 개선 과정 | 재질문 수 × 3점(최대 12점) + 답안 수정 이력 수(최대 8점) + 다듬어 달라는 재요청이 있으면 5점. 300자 이상을 붙여넣고 거의 고치지 않았으면 3점 뺌 | 다듬어 달라고 한 질문 |

답변 검증 (명세 9절: 학습자가 AI의 답을 원자료와 대조한 근거가 있어야 점수를 준다. 첫 질문은 근거로 쓰지 않는다):

| 경우 | 점수 (배점 20점일 때) | 근거 |
|---|---|---|
| AI가 틀리게 말한 사실을 짚어 바로잡음 | 답안에 올바른 값이 있으면 20, 틀린 값이 남았으면 9, 둘 다 없으면 16 | 짚어 물은 질문 |
| AI의 답을 받은 뒤 자료와 대조해 달라고 함 (AI가 아직 틀린 값을 말하지 않았을 때) | 답안에 올바른 값이 있으면 14, 없으면 10 | 그 질문 |
| 대조해 달라고 했지만 AI가 말한 틀린 값은 짚지 못함 | 6 | 그 질문 |
| 대화에서는 짚지 않았지만, 답안에 쓴 틀린 값을 나중에 자료의 값으로 고침 | 11 | 답안 수정 이력 (결과 API에는 내보내지 않고 피드백에 적는다) |
| 그 밖 | 0 | 없음 |

- 답변 검증이 양수이면 피드백에 무엇을 어떤 자료와 대조했는지(예: "새 선적 일정을 선적 일정표와 대조해")를 적는다.
- 채점 결과는 저장하기 전에 검사한다(`validateGrade`): 네 항목이 한 번씩 있는지, 점수가 0~배점의 정수인지, 근거 대화가 이 응시의 것인지, 필수 요건 ID가 스냅샷과 정확히 같은지, 답변 검증이 양수인데 근거가 없지 않은지. 어긋나면 채점 실패(`GRADING_FAILED`)가 된다. 스냅샷에 판정 규칙을 모르는 필수 요건이 있어도 건너뛰지 않고 채점 실패다.
- 항목별 피드백은 배점 대비 비율 구간(80% 이상, 52% 이상, 그 밖)과 실제로 빠진 요소에 따라 다른 문장을 쓴다. 총평(`summary_feedback`)은 통과면 가장 좋았던 항목, 미달이면 통과하지 못한 이유 두 가지까지와, 과제마다 정해 둔 "현업에서 다시 쓸 행동 한 가지"(`practice`)를 담는다.
- 예전 기준(`LEGACY_TOTAL_V1`)의 응시는 같은 규칙으로 25점 배점에 맞춰 매기고, 총점 80점 이상이면 통과다. 필수 요건 판정은 하지 않는다(`required_check_results`가 `null`).
- 레벨은 채점이 끝날 때 `min(1 + 통과한 서로 다른 과제 수, 6)`으로 다시 계산하고, 오르면 WebSocket으로 `player_updated`를 모두에게 보낸다.
- 점검 예시(과제 1): 역할과 조건을 주고 묻고, 틀린 일정을 짚어 바로잡고, 어조를 다시 요청하며 답안을 고친 응시는 95점(실무 과제 해결 50, AI 활용 역량 45)으로 통과였다. 같은 대화에 창고 입고 예상일(12월 3일)을 확정처럼 약속한 답안은 95점이지만 필수 요건 미충족으로 미통과, "회신 메일 초안을 써 줘" 한 번만 묻고 틀린 일정을 그대로 쓴 답안은 34점(필수 요건 미충족, 답변 검증 0점)이었다.

### 과제별 필수 요건

판정 규칙의 원문(`rule`)은 `mock/content.ts`에 있고 응답에는 내보내지 않는다. 모의 서버는 `judges`의 정해진 규칙으로 판정한다.

| 과제 | `check_id` | 공개 설명(`label`) | 모의 판정 |
|---|---|---|---|
| 1 | `SHIPPING_DATE` | 확정 선적일을 정확히 안내하고 미확정 일정을 확정처럼 약속하지 않기 (명세 예시) | 답안에 11월 17일 출항이 있고, 11월 21일·12월 6일이 없고, 12월 3일(일정표의 예상 입고일)을 "expect·예상" 같은 말 없이 약속한 문장이 없으면 충족 |
| 2 | `QUOTE_PRICE` | 단가표의 수량 할인만 적용해 모델별 단가와 두 조건의 합계를 정확히 적기 | USD 11.40, 26,800, 28,745가 모두 있고 10% 할인 값이 없으면 충족 |
| 2 | `QUOTE_TERMS` | 결제 조건, 납기, 견적 유효기간을 모두 밝히기 | 세 가지에 해당하는 말이 모두 있으면 충족 |
| 3 | `LC_SHIPMENT_DATE` | 신용장의 최종 선적일이 선적 계획과 맞지 않는 점을 짚고 수정을 요청하기 | 44C나 12월 5일을 짚고, 수정 요청이 있고, 12월 25일이 없으면 충족 |
| 4 | `BL_NUMBERS` | 세 서류의 숫자 항목(박스 수, 중량)을 모두 대조해 다른 곳을 정정 항목에 넣기 | 330(박스 수)과 6,240(중량)이 모두 있고 "중량이 일치"라는 문장이 없으면 충족 |
| 5 | `EXPORT_SHIP_DEADLINE` | 수출신고 수리 뒤 선적해야 하는 기한을 사내 안내 자료대로 정확히 적기 | 30일이 있고 60일이 없으면 충족 |

## 명세와 다르게 흉내 낸 부분

| 항목 | 명세 | 모의 서버 |
|---|---|---|
| 비밀번호 해시 | bcrypt | Node 내장 `crypto.scrypt`. 의존성을 늘리지 않기 위해서다 |
| 액세스 토큰 | JWT(HS256), 서명 키는 `JWT_SECRET` | JWT 모양 그대로 HS256으로 서명하지만 키는 코드에 고정. 페이로드에 명세에 없는 `ep`(초기화 회차)와 `jti`(토큰마다 다른 값)를 더 넣는다 |
| 동시성 처리 | `SELECT ... FOR UPDATE`, 조건부 UPDATE | 한 프로세스의 메모리에서 순서대로 처리하므로 잠금이 없다 |
| 응시의 `auto_submitted` | ERD에 컬럼이 없음 | 응시 데이터에 따로 둔다 |
| 자동 제출 시각 | 정하지 않음 | `submitted_at`을 "마감 + 1분"으로 둔다 |
| 리프레시 토큰 쿠키의 `Secure` | 배포 환경에서 켬 | 개발용이라 붙이지 않는다 |
| 서버 재시작 때 채점 중 응시 | `GRADING_FAILED`로 바꿈 | 같다. 모의 서버 파일을 고치면 Vite가 서버를 다시 띄우므로, 그때 채점 중이던 응시는 재채점해야 한다 |
| `player_updated` 받는 사람 | "모두에게" | 레벨이 오른 본인을 포함해 접속자 전원에게 보낸다 |
| 같은 계정 재접속 | 기존 연결 4409 | 기존 연결을 4409로 닫고, 다른 접속자에게는 `player_left` 뒤 `player_joined`를 보낸다 (새 연결은 시작 위치에서 다시 시작하므로) |
| 422 응답 | FastAPI 기본 형식 | `{"detail":[{"type","loc","msg","input","ctx"}]}` 모양을 흉내 낸다. `type`과 `msg` 문구가 pydantic과 모두 같지는 않다 |
| 이벤트 `payload` 1KB 초과 | 규칙만 있음 | 422로 거절한다 |

## 검증

```bash
npx tsc --noEmit -p tsconfig.node.json      # mock/와 vite.config.ts 타입 검사
npx vite --port 5180 --strictPort           # 다른 창에서 서버를 띄운 뒤
node mock/smoke.mjs http://localhost:5180   # 주요 흐름 검사. 마지막 줄에 passed N, failed M
```

`smoke.mjs`는 시작할 때 데이터를 초기화하고 새로 가입한 계정으로 검사한다. 끝나면 다시 초기화한다. 하나라도 실패하면 종료 코드가 1이다. WebSocket의 5초 인증 시간 초과와 채점 대기 때문에 30~40초 걸린다.
