# 판단 기록

픽셀 키트를 입힌 화면을 만들면서 내린 판단을 내린 순서대로 적는다. 판단은 모두 작업자(Claude)가 스스로 내렸다. 1~7절은 PoC(방향을 확인하려고 작게 만든 시제품)를 만들 때의 판단이고 2026-11-20에 방향을 확인받았다. 8절은 그 뒤 실제 맵으로 옮기고 다듬으면서 내린 판단이고 확인받지 않은 상태다. 틀렸다고 보이는 줄이 있으면 그 번호를 알려 주면 된다.

나중의 판단이 앞의 판단을 바꾼 경우에는 앞의 줄을 지우지 않고 "→ 몇 번에서 바뀜"이라고 적었다.

무게가 큰 결정은 [ADR](adr/)로 따로 적었고 여기서는 한 줄로 가리킨다. 아직 답이 없는 것은 [확인이 필요한 것](open-questions.md)에 모았다.

## 1. 시작하기 전: 무엇을 만들 것인가

| 번호 | 상황 | 판단 | 이유 |
|---|---|---|---|
| 1 | "기존 UI에 적용"이라고 했는데 `main`에는 초기 세팅 문구 한 줄뿐이었다. 팀원의 PR #1(교실 데모와 강의 팝업)이 열려 있었다 | "기존 UI"를 PR #1의 코드로 보고 그 위에 쌓았다 | `main`에서 따로 시작하면 같은 파일이 충돌한다. PR #1이 폴더 구조와 이벤트 방식을 이미 정해 두었다 → [ADR 0006](adr/0006-build-on-teammate-branch-and-event-contract.md) |
| 2 | PoC의 범위를 어디까지로 할 것인가 | 가입부터 레벨업까지 **한 바퀴 전체**를 얕게가 아니라 실제로 동작하게 만들었다 | 화면 한두 개로는 "키트가 서비스 전체의 겉모습이 되는가", "한 바퀴가 자연스러운가"를 확인할 수 없다. 대신 맵 꾸미기, 확장 계획의 기능, 화면 테스트는 뺐다 |
| 3 | 맵은 다른 팀원의 작업이다 | 임시 광장을 새 씬으로 만들고 팀원의 `Classroom.ts`는 건드리지 않았다. 배치는 파일 하나에 모았다 → 50번에서 바뀜 | 한 바퀴를 돌려면 걸어 다닐 곳이 필요하지만, 팀원의 작업을 덮어쓰면 안 된다 |
| 4 | 와이어프레임(Figma)을 열 수 없었다 (접근 권한 없음) | 기획서의 유저 플로우와 API 명세의 "화면별 사용 API"를 근거로 화면을 구성했다 | 권한을 기다리며 멈추는 것보다, 근거를 밝히고 진행한 뒤 대조하는 편이 낫다 |
| 5 | 기획서가 가리키는 `userflow.md`가 받은 문서에 없었다 | 예외 흐름을 API 명세의 에러 코드에서 거꾸로 정했다 | 에러 코드마다 "프론트는 이렇게 한다"가 명세에 적혀 있다 |
| 6 | 루트에 `기획서/`, `설계/`, `청년 유치원 픽셀 키트/` 폴더가 git에 올라가지 않은 채 있었다 | 저장소에 올리지 않고 읽기만 했다. 키트 소스만 `src/pixel-kit/`에 복사했다 | 기획과 설계 문서는 다른 곳에서 관리되는 것으로 보인다. 같은 문서가 두 곳에 있으면 갈라진다 |

## 2. 기반: 통신, 상태, 겉모습

| 번호 | 상황 | 판단 | 이유 |
|---|---|---|---|
| 7 | 모의 서버를 어디에 둘 것인가 | Vite 개발 서버의 플러그인으로 | 쿠키, WebSocket, 여러 브라우저의 상태 공유가 실제로 동작해야 한다 → [ADR 0001](adr/0001-mock-server-as-vite-plugin.md) |
| 8 | 키트(자바스크립트)를 TypeScript 프로젝트에 어떻게 들일 것인가 | 원본 그대로 복사하고 타입 선언만 따로 → 복사한 위치는 52번에서 바뀜 | 새 버전을 덮어쓰기 쉽게 → [ADR 0002](adr/0002-vendor-pixel-kit.md) |
| 9 | API 응답의 필드 이름을 화면에서 `camelCase`로 바꿀 것인가 | 명세의 `snake_case`를 그대로 쓴다 | 바꾸는 층을 두면 명세와 코드를 대조할 때 한 번 더 번역해야 한다. 23개 API 전부에 변환 코드가 필요하다 |
| 10 | 액세스 토큰을 어디에 둘 것인가 | 메모리에만 둔다. 새로고침하면 쿠키로 다시 받는다 | 명세가 정한 방식이다 |
| 11 | 여러 요청이 동시에 "토큰 만료"를 받으면 | 재발급 요청은 한 번만 보내고 나머지는 그 결과를 기다린다 | 명세가 요구한다. 재발급할 때마다 리프레시 토큰이 교체되므로, 두 번 보내면 하나는 반드시 실패한다 |
| 12 | 주소 이동(라우터)을 넣을 것인가 | 넣지 않는다 | 기획이 "화면 전환 없음"이다 → [ADR 0003](adr/0003-overlays-on-one-map-no-router.md) |
| 13 | 상태 관리 라이브러리를 넣을 것인가 | 넣지 않는다 | 데이터가 적다 → [ADR 0007](adr/0007-no-state-library.md) |
| 14 | 글꼴 | 짧은 글은 픽셀 글꼴(Galmuri11), 읽는 글은 고딕 | 시험 화면의 긴 글을 읽기 편하게 → [ADR 0004](adr/0004-pixel-look-with-readable-body.md) |
| 15 | 글꼴을 어디서 받아올 것인가 | npm 패키지로 들여와 함께 배포한다 | 외부 글꼴 서버에 접속하지 못하는 환경(사내망, 오프라인 발표)에서도 같은 모습이어야 한다 |
| 16 | 픽셀 테두리를 어떻게 그릴 것인가 | 네 변을 그림자로 따로 그린다 (`px-box`) | 모서리가 한 칸 비어 도트 그림처럼 보인다. 이미지 파일이 필요 없다 |
| 17 | 창이 떠 있을 때 캐릭터를 멈추는 일을 누가 맡는가 | 창 부품(`Dialog`)이 스스로 알린다. 창이 여러 개여도 개수를 세어 마지막 창이 닫힐 때만 풀린다 | PR #1은 `App.tsx`가 창마다 알렸다. 창이 늘어나면 빠뜨리기 쉽다 |
| 18 | 맵이 화면보다 늦게 준비돼서 "창이 열렸다"는 알림을 놓친다 | 이벤트의 가장 최근 값을 물어보는 `current()`를 추가했다 | 첫 입장 안내 창 뒤에서 캐릭터가 움직이는 문제를 막는다 |

| 33 | 모의 AI가 언제나 옳은 답만 하면 "답변 검증" 항목을 확인할 수 없다 | 과제마다 AI가 자료와 다른 사실을 하나 섞어 말하게 했다 | 기획서의 피드백 예시가 "AI가 잘못 말한 선적일을 일정표로 바로잡았어요"다 |
| 34 | 서브에이전트에 작업을 나눠 맡겼다 (모의 서버, 맵, 로그인·HUD·강의, 시험) | 맡기기 전에 통신 코드, 타입, 공통 부품, 컴포넌트의 이름과 인자를 먼저 정해 두었다. 에이전트마다 고쳐도 되는 폴더를 못 박고 git 명령을 금지했다 | 네 작업이 같은 폴더에서 동시에 돈다. 경계를 먼저 정하지 않으면 서로의 파일을 고친다 |

## 6. 합치고 검증하면서

| 번호 | 상황 | 판단 | 이유 |
|---|---|---|---|
| 35 | 키트의 외형 갱신 함수(`updateCharacter`)가 Phaser 4에서 화면을 멈췄다. 쓰는 중인 그림을 먼저 지우는 순서 때문이다 | 키트는 고치지 않고 `src/game/character/kit.ts`에서 같은 그림판에 새 그림을 덮어 그리게 했다 | 키트를 고치면 새 버전을 덮어쓸 때 수정이 사라진다 ([ADR 0002](adr/0002-vendor-pixel-kit.md)). 키트를 만든 쪽에 알려야 한다 |
| 36 | 화면을 찍어 보니 왼쪽 위의 내 정보 카드가 강의장과 칠판을 가렸다 | 내 정보와 "지금 할 일"을 왼쪽 아래로 옮겼다 (실제 맵에서도 이 자리를 유지했다. 54번) | 기획서의 맵 구성에서 왼쪽 위는 강의장이다. 왼쪽 아래의 상담실은 MVP에서 배경만 있는 구역이라 가려도 손해가 가장 작다. 실제 맵의 배치가 정해지면 다시 본다 |
| 37 | 창을 두 개 겹치면 `Esc` 한 번에 둘 다 닫혔다 | 맨 위 창만 키를 받게 했다 | 확인 창을 닫으려다 뒤의 창까지 닫히면 하던 일을 잃는다 |
| 38 | 창이 열릴 때마다 창 전체에 파란 초점 테두리가 보였다 | 전역 초점 규칙을 Tailwind의 기본 층(`@layer base`)으로 내렸다 | 부품이 테두리를 끌 수 있어야 한다. 키보드로 옮긴 초점의 표시는 그대로다 |
| 39 | 움직임 줄이기 설정에서 깜빡임 애니메이션이 오히려 아주 빠르게 반복됐다 | 그 설정에서는 애니메이션을 한 번만 재생하게 했다 | 움직임을 줄여 달라는 사용자에게 더 심한 깜빡임을 보이면 안 된다 |
| 40 | 재발급한 뒤에도 멀티플레이 인증이 실패하면 화면은 "다시 연결하는 중"에 머물렀다 | 로그인이 풀렸다고 알리는 함수(`notifySessionLost`)를 통신 코드에 추가해 로그인 화면으로 보낸다 | 명세가 "또 실패하면 로그인 화면"이라고 정한다 |
| 41 | 백엔드 주소의 환경 변수 이름이 `VITE_`로 시작했다 | `API_TARGET`으로 바꿨다 | `VITE_`로 시작하는 값은 브라우저로 가는 묶음에 들어갈 수 있다. 이 값은 개발 서버만 알면 된다 |
| 42 | 모의 서버의 타입 검사가 빌드에 빠져 있었다 | `npm run build`가 화면과 모의 서버를 모두 타입 검사하게 했다 | 검사가 조용히 빠지는 구조를 만들지 않는다 |
| 43 | AI 시험관의 골드 모자가 Lv.1 노랑 모자와 거의 같은 색으로 보인다 | 그대로 두고 [확인이 필요한 것](open-questions.md)에 적었다. 맵에서는 이름표의 "AI" 표시로 구분한다 | 색은 키트의 것이고, 키트는 고치지 않기로 했다 |
| 44 | 서브에이전트의 보고에 "확인하지 못함"으로 적힌 항목들 | 합친 뒤 브라우저 자동화로 한 바퀴를 직접 밟아 다시 확인했다. 그래도 확인하지 못한 것은 [검증 결과](verification.md)에 남겼다 | 보고를 그대로 믿지 않는다. 각 에이전트는 임시 화면에서만 확인했고 실제 앱과 모의 서버를 붙여 본 적이 없었다 |

## 8. 방향을 확인받은 뒤: 실제 맵으로 옮기고 다듬기

2026-11-20에 PoC의 방향을 확인받았다. "브랜치를 만들고, 중간중간 커밋하고, 문서를 다듬어 완성도를 높여 PR을 올린다"는 요청이었다.

## 9. 공통 API 모듈

2026-11-20에 "공통 모듈로 쓸 수 있는 API 코드를 만든다. 공개된 오픈소스의 방식이나 확장성 좋고 쓰기 쉬운 방식을 쓴다"는 요청을 받았다.

| 번호 | 상황 | 판단 | 이유 |
|---|---|---|---|
| 67 | 통신 코드가 이미 있다. 새로 만들 것인가 고칠 것인가 | 기존 `api.xxx()` 호출이 그대로 동작하게 두고 그 아래를 바꿨다 | 가져다 쓰는 곳이 45곳이다. 호출하는 쪽을 깨지 않으면 화면을 한꺼번에 고치지 않아도 된다 |
| 68 | 요청을 보내는 층에 라이브러리(ky, axios)를 쓸 것인가 | ky의 구성(인스턴스, 요청별 옵션, 시간 제한, 안전한 요청만 다시 시도, 훅)을 따라 직접 썼다 | 재발급 규칙과 명세의 에러 형식은 어차피 직접 써야 하고, 나머지가 약 290줄이다 → [ADR 0009](adr/0009-api-module-own-client-and-tanstack-query.md) |
| 69 | 서버 데이터를 화면에 주는 층 | TanStack Query를 들였다. 13번의 판단을 바꾼 것이다 | 13번에서 적어 둔 "다시 검토할 신호"(같은 데이터를 여러 곳에서 따로 부름, 같은 모양의 코드 반복)가 나타났다. 직접 만들면 라이브러리를 다시 만드는 셈이다 → [ADR 0009](adr/0009-api-module-own-client-and-tanstack-query.md) |
| 70 | 무엇을 다시 시도할 것인가 | 조회(GET)만, 서버에 닿지 못했거나 502·503·504일 때 | 만들기와 제출을 다시 보내면 두 번 처리될 수 있다. 4xx는 다시 보내도 같은 답이다 |
| 71 | 다시 시도가 HTTP 클라이언트와 조회 저장소 두 곳에 있다 | 조회 저장소는 서버에 닿지 못한 경우만 한 번 더 시도하게 했다 | 겹치면 실패 하나에 아홉 번까지 보낸다 |
| 72 | `GET /attempts/current`는 부를 때마다 서버가 자동 제출을 처리한다 | 결과를 저장해 두지 않게 했다 | 조회처럼 생겼지만 저장해 둔 값을 보여 주면 이미 제출된 시험을 "이어 풀기"로 보여 줄 수 있다 |
| 73 | 창을 열 때 저장해 둔 값(10초)을 보여 주면 방금 들은 강의의 수강률이 옛 값으로 보인다 | 강의 대시보드와 과제 목록은 열 때마다 새로 받게 했다. 저장해 둔 값을 먼저 보여 주고 뒤에서 바꾼다 | 수강률과 응시 가능 여부는 방금 바뀌었을 가능성이 높은 값이다 |
| 74 | 기존 화면을 모두 훅으로 옮길 것인가 | 여러 화면이 함께 보는 값을 쓰는 세 곳만 옮겼다 | 나머지는 지금도 올바르게 동작한다. 한꺼번에 옮기면 시험 화면처럼 검증이 무거운 곳을 이유 없이 건드리게 된다. 옮긴 곳과 남은 곳은 [사용법 문서](api-module.md)에 적었다 |
| 75 | 테스트를 쓰다가 이미 끊긴 신호로 부른 요청이 끝나지 않는 것을 찾았다 | 보내기 전에 신호를 확인해 바로 실패시킨다 | 닫힌 화면의 요청은 보내지 않는 것이 맞다 |
| 76 | 화면이 `api/client`, `api/endpoints`, `api/types` 세 곳에서 따로 가져다 썼다 | 입구를 `src/api/index.ts` 하나로 모으고 가져오는 경로 45곳을 바꿨다 | 안쪽 구조를 바꿔도 화면을 고치지 않게 하려는 것이다 |
| 77 | OpenAPI 문서에서 타입과 함수를 자동으로 만드는 방식 | 지금은 하지 않고 ADR에 남겼다 | 백엔드에 API가 아직 하나도 없어 원본이 없다. 백엔드가 올라오면 검토한다 |

### 범위를 바로잡음

PR을 올린 뒤 "명세의 API를 전부 개발하라는 것이 아니다. 팀원과 분야를 나눠 개발할 것이니 공통 코드만 만든다"는 말을 들었다. 처음 올린 PR에는 모든 분야의 조회와 변경 훅(응시 결과 조회, 제출, 포기, 재채점, AI 질문 등 열다섯 개 남짓)이 들어 있었다. 요청을 넓게 읽은 것이다.

| 번호 | 상황 | 판단 | 이유 |
|---|---|---|---|
| 78 | 미리 만들어 둔 분야별 훅 | 쓰이지 않는 것을 모두 지웠다. 남긴 것은 여러 화면이 함께 보는 값의 조회 셋(내 정보, 강의 대시보드, 과제 목록)과 수강률이 바뀌었다고 알리는 함수 하나다 | 분야별 훅은 그 분야를 맡은 사람이 자기 화면에 맞게 정해야 한다. 쓰이지 않는 코드는 아무도 검증하지 않은 채 남는다 |
| 79 | API 함수 23개가 파일 하나에 있다. 여러 사람이 분야를 나눠 고치면 같은 파일에서 충돌한다 | 분야별 파일 다섯 개(`domains/`)로 나눴다. 함수의 내용은 바꾸지 않았다. `api.xxx()`로 부르는 방식도 그대로다 | 자기 분야의 파일만 고치면 다른 사람과 같은 줄을 고칠 일이 없다 |
| 80 | 조회의 이름표와 훅을 어디에 둘 것인가 | 공통 파일 하나가 아니라 각 분야별 파일에 둔다 | 공통 파일 하나에 모으면 79번과 같은 충돌이 다시 생긴다 |
| 81 | 토큰 재발급은 인증 분야인가 공통인가 | 공통(`client.ts`)에 두었다 | 모든 요청이 기대는 동작이다. 인증을 맡은 사람이 바뀌어도 흔들리면 안 된다 |
| 82 | 응시 분야에서 조심할 규칙(자동 제출의 부수 효과, 응시가 바뀌면 과제와 레벨도 낡음)을 훅으로 구현해 두었다가 지웠다 | 구현 대신 그 분야 파일의 주석과 공통 옵션(`NEVER_CACHE`)으로 남겼다 | 지식은 넘기되 구현은 담당자에게 맡긴다 |
| 83 | 응답 타입(`types.ts`)도 분야별로 나눌 것인가 | 나누지 않았다. 확인이 필요한 것으로 남겼다 | 화면 45곳이 이 타입을 쓴다. 나누는 것 자체는 쉽지만, 팀이 분야를 어떻게 나누는지 모르는 채로 경계를 정하면 다시 옮겨야 한다 |
| 84 | 분야를 누가 맡는지 모른다 | 파일마다 "담당자가 정해지면 이 파일을 맡는다"고만 적었다 | 지어내지 않는다 |
