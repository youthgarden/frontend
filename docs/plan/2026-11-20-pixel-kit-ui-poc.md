# 계획: 픽셀 키트를 입힌 화면과 모의 서버

이 문서는 **무엇을 어떤 순서로 만들었고 무엇이 남았는지**를 적는다. 왜 이런 모양인지는 [의도 문서](../intent/2026-11-20-pixel-kit-ui-poc.md)에 있다.

## 목표

모의 서버만으로 "가입 → 강의 수강 → 시험 → 채점 → 레벨업" 한 바퀴가 픽셀 키트의 겉모습으로, 팀원이 만든 실제 맵 위에서 동작한다.

## 단계

PoC(Proof of Concept)는 방향이 맞는지 확인하려고 작게 만들어 보는 시제품이다. 먼저 PoC로 방향을 확인받고 나서 완성했다.

| 단계 | 내용 | 끝났다고 본 기준 | 상태 |
|---|---|---|---|
| 0. 읽기 | 기획서, ERD, API 명세, 픽셀 키트, 팀원의 PR #1 | 화면 목록과 화면별 API를 말할 수 있다 | 끝 |
| 1. 기반 | 키트의 타입 선언, API 타입과 통신 코드, 로그인 상태, 디자인 토큰과 공통 부품, 앱의 뼈대 | 뼈대만으로 빌드가 통과한다 | 끝 |
| 2. 화면과 서버 (네 갈래로 동시에) | 모의 서버 / 임시 광장과 캐릭터와 멀티플레이 / 로그인·HUD·강의·레벨업 / 시험장 흐름 | 갈래마다 타입 검사가 통과한다 | 끝 |
| 3. 합치기 | 네 갈래를 합쳐 빌드, 모의 서버 흐름 확인, 브라우저로 한 바퀴 | 빌드 통과, 스크립트 실패 0건, 한 바퀴를 화면으로 확인 | 끝 |
| 4. 방향 확인 | 개발 서버를 띄우고 방향 정리 문서와 함께 확인받는다 | 방향에 대한 답을 받는다 | 끝 (2026-11-20, 방향 그대로 진행) |
| 5. 실제 맵으로 옮기기 | 팀원의 `feat/world-map` 위로 옮긴다. 임시 광장을 버리고, 맵의 캐릭터 자리와 패널 자리를 채운다 | 실제 맵에서 한 바퀴가 돈다 | 끝 |
| 6. 다듬기 | 단위 테스트, 한 바퀴에서 밟지 않은 상태 확인, 화면을 보고 고치기, 문서 정리 | [검증 결과](../verification.md)의 숫자가 채워진다 | 끝 |
| 7. PR | 맵 담당의 파일을 고친 곳과 합의할 것을 정리해 올린다 | 리뷰를 받을 수 있는 상태 | 끝 (`main`에 들어감) |
| 8. 공통 API 모듈 | 통신 코드의 공통 부분(범용 클라이언트, 토큰, 조회 저장소)을 만들고, API 함수를 분야별 파일로 나눈다. 분야별 조회와 훅은 담당자가 채운다 | 한 바퀴가 그대로 돌고 테스트가 통과한다 | 끝 (`main`에 들어감) |
| 9. 분담 | 두 사람이 절반씩 맡도록 경계를 정하고 문서와 리뷰어 자동 지정에 반영한다 | [분담](../ownership.md)이 있다 | 끝 (`main`에 들어감) |
| 10. 검증받는 쪽 | 과제와 응시의 조회·변경 훅, 시험 쪽 화면 옮기기, 테스트, 키보드와 화면 낭독기 보완, 새 명세의 채점 방식 반영 | 한 바퀴가 그대로 돌고 새 채점 방식의 화면이 보인다 | **지금 여기** |

5단계는 처음 계획에 없었다. 방향을 확인받은 직후에 팀원의 실제 맵이 올라왔고, 임시 맵을 PR에 넣는 것보다 실제 맵 위에서 완성하는 편이 낫다고 판단했다 ([판단 기록](../decision-log.md) 8절).

## 코드의 구조

```
src/
  main.tsx, App.tsx      진입점. App이 "어떤 창이 떠 있는가"를 가진다
  events.ts              맵과 화면이 주고받는 이벤트 목록
  character.ts           캐릭터 외형 규칙, 레벨과 모자 색 정보
  api/                   서버와 주고받는 코드. 사용법은 docs/api-module.md
    index.ts             입구. 화면은 여기에서만 가져다 쓴다
    core/                (공통) 범용 HTTP 클라이언트와 ApiError
    client.ts            (공통) 이 서비스의 HTTP 클라이언트. 기본 주소, 토큰, 재발급
    query/               (공통) 조회 저장소의 기본값, 공통 옵션
    types/               API 명세의 응답 형식. 공통, 배우는 쪽, 검증받는 쪽으로 나뉜다
    domains/             (분야별) 인증, 회원, 강의, 과제, 응시. 분야를 맡은 사람이 채운다
    endpoints.ts         분야별 함수를 api 한 이름으로 모은다
  session/               로그인 상태, 내 정보, 강의·과제 현황
  game/                  Phaser 쪽
    PhaserGame.tsx
    scenes/              광장(World)과 건물 안(Room). 맵 담당의 코드
    player.ts            내 캐릭터의 이동과 상호작용 키. 그림은 CharacterView
    assets.ts            키트의 타일과 오브젝트 등록, 장면 전환. 맵 담당의 코드
    pixel-kit/           청년 유치원 픽셀 키트 원본(.js)과 타입 선언(index.d.ts)
    character/           캐릭터 그림, 이름표, 레벨별 모자
    net/                 멀티플레이: 연결(MapSocket), 게임 단위 상태(MapPresence), 광장에 그리기(RemotePlayers)
    mapSpec.ts           광장의 크기, 시작 위치 (모의 서버도 함께 읽는다)
  ui/                    React 쪽
    kit/                 공통 부품 (버튼, 판, 창, 캐릭터 그림, 진행 막대 ...)
    auth/                로그인, 회원가입
    hud/                 맵 위에 항상 떠 있는 정보, 첫 입장 안내
    lecture/             강의 대시보드, 강의 재생
    exam/                시험관 메뉴 → 과제 목록 → 과제 안내 → 시험 → 채점 → 결과, 지난 결과
    levelup/             레벨업 연출
    dev/                 모의 서버 조작판 (모의 서버로 띄웠을 때만 보인다)
mock/                    모의 서버 (Vite 플러그인). 배포 묶음에 들어가지 않는다
docs/                    이 문서들
```

## 화면과 API

| 화면 | 여는 방법 | 쓰는 API |
|---|---|---|
| 로그인, 회원가입 | 로그인하지 않았을 때 | `GET /jobs`, `POST /auth/signup`, `POST /auth/login` |
| 앱 시작 | 새로고침 | `POST /auth/refresh` → `GET /users/me` |
| 맵과 HUD | 로그인한 뒤 | `GET /users/me`, `GET /lectures`, `GET /tasks`, WebSocket `/ws/map` |
| 첫 입장 안내 | 처음 들어왔을 때, 조작법 버튼 | `PATCH /users/me` |
| 강의 대시보드 | 강의실 칠판 앞에서 `F` | `GET /lectures` |
| 강의 재생 | 대시보드에서 강의 선택 | `GET /lectures/{id}`, `POST /lectures/{id}/progress` |
| 시험관에게 말 걸기 | 시험장 접수 책상 앞에서 `F` | `GET /attempts/current` |
| 과제 목록 | 시험관 메뉴 "새 시험 보기" | `GET /tasks` |
| 과제 안내 | 과제 선택 | `GET /tasks/{id}` |
| 시험 | "시험 시작" 또는 "이어 풀기" | `POST /attempts`, `GET·POST /attempts/{id}/messages`, `PUT /attempts/{id}/answer`, `POST /attempts/{id}/events`, `POST /attempts/{id}/submit`, `DELETE /attempts/{id}` |
| 채점 대기 | 제출한 뒤 | `GET /attempts/{id}` (2초마다), `POST /attempts/{id}/regrade` |
| 결과 | 채점이 끝난 뒤, 지난 결과에서 선택 | `GET /attempts/{id}`, `GET /attempts/{id}/messages` |
| 지난 결과 | 시험관 메뉴 "지난 결과 보기" | `GET /attempts` |
| 레벨업 연출 | 레벨이 오른 결과를 처음 보고 맵으로 돌아올 때 | (없음. 결과의 `level_up`을 쓴다) |

## 작업을 나눈 방식

2단계와 5단계의 일부는 서브에이전트에 나눠 맡겼다. 같은 폴더에서 동시에 일하므로 아래를 지켰다.

- 맡기기 전에 서로 맞닿는 부분(API 타입, 통신 코드, 공통 부품, 컴포넌트의 이름과 인자, 이벤트 목록, 맵 좌표)을 먼저 확정했다.
- 갈래마다 고쳐도 되는 폴더를 지시서에 적었다. 다른 폴더는 읽기만 한다.
- git의 쓰기 명령과 패키지 설치를 금지했다. 검증과 커밋은 맡긴 쪽이 한다.
- 범위 밖의 문제는 고치지 말고 보고만 하게 했다. 이 규칙으로 드러난 것: 키트와 Phaser 4의 호환 문제, 맵의 `goto` 구독 누수, 명세의 빈틈 일곱 가지.
- 기준선(타입 오류 0건)과 앞에서 겪은 함정을 지시서에 적었다.
- 돌아온 보고는 그대로 믿지 않고 검증 명령을 다시 돌려 확인했다. 실제로 보고와 달랐던 것: 각 갈래는 임시 화면에서만 확인했고 합친 앱에서 확인한 것은 없었다.

## 검증

| 무엇을 | 어떻게 |
|---|---|
| 타입 | `npm run typecheck` (화면과 모의 서버) |
| 단위 테스트 | `npm test` |
| 빌드 | `npm run build` |
| 모의 서버의 흐름 | 서버를 띄운 뒤 `npm run mock:smoke -- http://localhost:5173` |
| 화면 한 바퀴 | 브라우저로 계정별 흐름을 직접 밟는다 |

실제 결과의 숫자는 [검증 결과](../verification.md)에 있다.

## 남은 일

| 할 일 | 끝났다고 보는 기준 |
|---|---|
| 맵 담당 팀원과 합의 ([확인이 필요한 것](../open-questions.md) 1~7번) | 이벤트 목록의 "제안" 표시가 사라진다 |
| 와이어프레임(Figma)과 화면 대조 | 다른 곳이 목록으로 정리되고 어느 쪽을 따를지 정해진다 |
| 실제 백엔드에 연결해 명세와 어긋나는 곳 찾기 | 모의 서버 없이 한 바퀴가 돈다 |
| 실제 강의 영상으로 시청 구간 측정 확인 | 영상을 끝까지 보면 수강 완료가 된다 |
| 화면 낭독기와 키보드만으로 다니는 흐름 점검, 화면 테스트 | 점검 결과가 목록으로 남는다 |
| 첫 화면 가볍게 하기 | 로그인 화면이 Phaser 없이 뜬다. 지금은 `events.ts`가 Phaser의 이벤트 도구를 쓰기 때문에 로그인 화면에서도 Phaser(묶음의 대부분, 약 2MB)가 함께 내려온다 |
| 글꼴 파일 줄이기 | 쓰는 글자만 남긴다. 지금은 두 파일이 약 670KB다 |
| 배우는 쪽의 조회와 훅 채우기, 새 명세 반영 | 검증받는 쪽은 끝났다. 배우는 쪽은 맡은 사람이 [사용법 문서](../api-module.md)의 순서대로 더한다. 새 명세와 어긋난 채로 남은 곳은 [확인이 필요한 것](../open-questions.md) 31~33번에 있다 |
| 강의에서 시험으로 넘어갈 때 그 강의의 과제 안내를 바로 열기 | 명세 10절의 동선이다. 두 쪽이 만나는 곳이라 합의하고 한다 ([확인이 필요한 것](../open-questions.md) 34~35번) |
| 1280px보다 좁은 화면의 시험 화면 | 자료와 답안을 함께 볼 수 있다 |
| 백엔드의 OpenAPI 문서에서 타입과 함수를 자동으로 만들기 | 백엔드가 올라온 뒤 검토한다 ([ADR 0009](../adr/0009-api-module-own-client-and-tanstack-query.md)) |
