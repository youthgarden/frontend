# ADR 0001: 모의 서버를 Vite 플러그인으로 띄운다

ADR(Architecture Decision Record)은 기술 결정을 하나씩 기록하는 문서다. 무엇을 정했는지와 함께 왜 그렇게 정했는지, 버린 선택지가 무엇인지를 남긴다.

- 상태: 적용 (방향 확인받음, 2026-11-20)
- 날짜: 2026-11-20

## 배경

백엔드 API가 아직 구현되지 않았다. 명세(`설계/2_API명세서.md`)는 REST API 23개와 WebSocket 하나를 정의한다. 프론트엔드는 이 명세만 보고 화면을 만들어야 하고, 만든 화면을 여러 상태의 사용자로 검수할 수 있어야 한다.

명세에는 화면 코드만으로는 흉내 내기 어려운 동작이 들어 있다.

- 리프레시 토큰은 `HttpOnly` 쿠키로 내려온다. 자바스크립트로 읽거나 쓸 수 없다.
- 멀티플레이는 WebSocket이다. 여러 탭과 여러 브라우저가 같은 상태를 봐야 한다.
- 채점은 제출 뒤 서버에서 비동기로 진행되고, 프론트엔드는 2초마다 결과를 물어본다.
- 시험 시간은 서버 시각이 기준이다. 나가 있는 동안에도 흐르고, 마감 뒤 1분이 지나면 서버가 자동으로 제출한다.

## 결정

모의 서버(mock server, 실제 서버 대신 약속된 응답을 돌려주는 가짜 서버)를 **Vite 개발 서버의 플러그인**으로 만든다. `npm run dev`를 실행하면 같은 포트에서 `/api/v1`의 REST 요청과 `/api/v1/ws/map`의 WebSocket 연결에 실제로 응답한다.

- 프론트엔드 코드는 모의 서버의 존재를 모른다. 언제나 `fetch('/api/v1/...')`와 `new WebSocket('/api/v1/ws/map')`을 쓴다.
- 환경 변수 `API_TARGET`에 실제 백엔드 주소를 넣으면 모의 서버가 꺼지고, `/api`가 그 주소로 넘어간다. 명세가 정한 "개발할 때는 Vite proxy로 `/api`를 백엔드에 넘긴다"와 같은 구조다.
- 검수용 조작(강의를 완료 처리, 남은 시간 변경, 채점 결과 강제)은 명세에 없는 주소 `/api/v1/__mock__/` 아래에만 둔다.

## 검토한 선택지

| 선택지 | 장점 | 버린 이유 |
|---|---|---|
| **Vite 플러그인 (채택)** | 실제 HTTP와 WebSocket이라 쿠키, 재발급, 멀티플레이, 폴링이 진짜로 동작한다. 여러 브라우저가 한 서버의 상태를 함께 본다. 실제 백엔드로 바꿀 때 프론트엔드 코드를 고치지 않는다 | |
| MSW (브라우저의 서비스 워커가 요청을 가로채는 라이브러리) | 백엔드 없이 정적 배포한 곳에서도 동작한다 | 상태가 브라우저마다 따로 생겨서 멀티플레이를 볼 수 없다. `HttpOnly` 쿠키를 그대로 흉내 내지 못한다. WebSocket 지원은 별도 구성이 필요하다 |
| API 함수를 가짜 구현으로 바꿔 끼우기 | 가장 빨리 만든다 | `fetch`, 토큰 재발급, 에러 형식 해석 같은 실제 통신 코드가 한 번도 실행되지 않은 채 남는다. 백엔드를 붙이는 날 한꺼번에 문제가 드러난다 |
| 별도의 Node 서버 프로세스 | 프론트엔드와 완전히 분리된다 | 실행할 것이 둘로 늘고 proxy 설정이 필요하다. PoC에는 과하다 |

## 결과

- 좋아지는 점: 통신 코드 전체가 PoC 단계부터 실제로 실행된다. 계정 여러 개로 탭을 나눠 열면 서로의 캐릭터가 보인다.
- 감수하는 점: 모의 서버는 `npm run dev`와 `npm run preview`에서만 동작한다. 백엔드 없이 정적 파일만 배포한 곳에서는 화면이 동작하지 않는다. 그런 배포가 필요해지면 그때 MSW를 추가로 검토한다.
- 감수하는 점: 모의 서버의 동작이 명세와 어긋나면 프론트엔드가 틀린 동작에 맞춰진다. 명세가 바뀌면 `mock/`도 함께 고친다. 흐름 전체를 확인하는 스크립트(`mock/smoke.mjs`)를 둔다.
- 모의 서버 전용 의존성 `ws`는 `devDependencies`에만 들어가고 배포 묶음에는 포함되지 않는다.

사용법은 [`docs/mock-server.md`](../mock-server.md)에 있다.
