# ADR 0009: 통신은 직접 만든 얇은 클라이언트로, 서버 데이터는 TanStack Query로

- 상태: 제안 (PR에서 확인 필요). [ADR 0007](0007-no-state-library.md)의 "서버 데이터 라이브러리를 넣지 않는다"를 바꾼다
- 날짜: 2026-11-20

## 배경

화면이 모두 만들어진 뒤 통신 코드를 다시 보니 두 가지가 드러났다.

첫째, 통신 코드에 빠진 것이 있었다. 응답이 오지 않으면 끝없이 기다렸고, 화면이 닫혀도 요청이 계속됐고, 서버가 잠깐 답하지 못해도 바로 실패로 보였다. 모든 요청에 무언가를 끼워 넣을 자리도 없었다.

둘째, [ADR 0007](0007-no-state-library.md)이 적어 둔 "다시 검토할 신호"가 이미 나타났다.

- "같은 데이터를 세 곳 이상에서 따로 불러오기 시작할 때": 강의 목록을 로그인 상태, 강의 대시보드가 따로 불렀고, 과제 목록을 로그인 상태, 과제 목록 창이 따로 불렀다.
- 화면마다 "불러오는 중, 실패, 다시 시도, 닫히면 무시"를 손으로 썼다. 같은 모양의 코드가 여섯 군데 있었다.
- HUD의 숫자를 맞추는 장치가 "창을 닫을 때 `App.tsx`가 다시 부른다" 하나뿐이었다. 창을 닫지 않고 값이 바뀌는 경우는 맞지 않는다.

## 결정

통신을 두 층으로 나누고 층마다 다르게 정한다.

### 1. 요청을 보내는 층: 직접 만든 얇은 클라이언트

`src/api/core/createClient.ts`에 `fetch`를 한 겹 감싼 클라이언트를 둔다. 구성은 오픈소스 **ky**의 방식을 따랐다.

| ky에서 가져온 방식 | 여기서의 모습 |
|---|---|
| 기본값을 가진 인스턴스와 `extend` | `createClient({ baseUrl, ... })`, `http.extend({ ... })` |
| 요청마다 덮어쓰는 옵션 | 모든 함수의 마지막 인자 `{ signal, timeoutMs, retry, query }` |
| 시간 제한 | 기본 15초. `TIMEOUT`으로 실패한다 |
| 안전한 요청만 다시 시도 | 조회(GET)만, 서버에 닿지 못했거나 502·503·504일 때, 간격을 늘려 가며 두 번 |
| 훅 | `beforeRequest`, `afterResponse`, `onError` |

이 서비스의 규칙(기본 주소, 토큰, 재발급)은 `src/api/client.ts`에 따로 둔다. 범용 클라이언트는 "로그인을 다루는 방식"을 인자로 받을 뿐 토큰이 어디에 있는지 모른다.

### 2. 서버 데이터를 화면에 주는 층: TanStack Query

조회 결과의 보관, 같은 조회 합치기, 화면이 닫힐 때 끊기, 일정 간격으로 다시 묻기, "이 값은 낡았다"는 표시는 **TanStack Query**에 맡긴다. 이름표와 불러오는 방법은 화면이 아니라 분야별 파일에서만 만든다(그 라이브러리가 권하는 "query key factory와 `queryOptions`" 방식).

"무엇이 바뀌면 무엇이 낡는가"는 서버의 규칙이므로 화면이 각자 판단하지 않고 분야별 파일에 함수로 둔다.

### 3. 공통 부분과 분야별 부분을 나눈다

API는 팀원이 분야를 나눠 맡는다. 그래서 모듈을 둘로 나눴다.

| 부분 | 내용 | 누가 고치는가 |
|---|---|---|
| 공통 | 범용 클라이언트, 실패 다루기, 토큰과 재발급, 조회 저장소의 기본값, 공통 옵션 | 팀에 알리고 고친다 |
| 분야별 (`src/api/domains/`) | 인증, 회원, 강의, 과제, 응시. 분야마다 파일 하나에 API 함수, 이름표, 훅을 둔다 | 그 분야를 맡은 사람 |

이 결정으로 만든 것은 공통 부분까지다. 분야별 파일에는 화면이 이미 쓰고 있던 API 함수를 옮겨 놓았고, 조회와 훅은 여러 화면이 함께 보는 값(내 정보, 강의 대시보드, 과제 목록)에만 두었다. 나머지 조회와 변경 훅은 미리 만들지 않았다. 담당자가 자기 화면에 맞게 정해야 하고, 쓰이지 않는 코드를 남기지 않기 위해서다.

### 4. 기존 화면은 한꺼번에 고치지 않는다

`api.xxx()` 호출은 그대로 동작한다. 여러 화면이 함께 보는 값을 쓰는 세 곳(로그인 상태, 강의 대시보드, 과제 목록)만 훅으로 옮겼다. 나머지는 그 분야를 맡은 사람이 화면을 고칠 때 옮긴다.

## 검토한 선택지

### 요청을 보내는 층

| 선택지 | 버린 이유 |
|---|---|
| **직접 만든 얇은 클라이언트 (채택)** | |
| ky를 그대로 설치 | 가장 가까운 선택지다. 버린 이유는 둘이다. 첫째, 이 서비스의 "재발급은 한 번만, 그 뒤 원래 요청을 한 번 다시"를 ky의 훅 안에서 구현하면 다시 시도 횟수와 얽혀 읽기 어렵다. 둘째, 실패를 명세의 에러 형식(`code`, `message`)으로 바꾸는 코드는 어차피 써야 한다. 필요한 기능을 직접 쓰니 약 290줄이었고 테스트 18건으로 덮었다. 요구가 늘어 이 파일이 커지면 ky로 바꾼다. 화면은 `api`만 부르므로 바꿔도 화면은 그대로다 |
| axios | `fetch`가 없던 시절의 도구다. 묶음이 커지고(약 13KB), 요청을 끊는 방식과 실패의 모양이 `fetch`와 달라 TanStack Query의 `signal`을 넘기는 데 한 겹이 더 필요하다 |
| OpenAPI 문서에서 클라이언트를 자동 생성 (openapi-fetch, orval) | 백엔드가 FastAPI라서 OpenAPI 문서가 나온다. 가장 바람직한 끝 모습이다. 지금은 백엔드에 API가 하나도 없어서 생성할 원본이 없다. 백엔드가 올라오면 `types.ts`와 `endpoints.ts`를 생성물로 바꾸는 것을 검토한다 |

### 서버 데이터를 화면에 주는 층

| 선택지 | 버린 이유 |
|---|---|
| **TanStack Query (채택)** | |
| 직접 만든 `useApiQuery` 훅 | 처음에는 쉬워 보이지만 같은 조회 합치기, 늦게 온 응답 버리기, 낡음 표시, 간격을 두고 다시 묻기를 다 만들면 라이브러리를 다시 만드는 셈이다. 이런 코드에서 찾기 어려운 버그가 난다 |
| SWR | 같은 일을 한다. 값을 바꾼 뒤 조회를 낡게 표시하는 기능과 변경 훅이 TanStack Query 쪽이 더 갖춰져 있고, 이 서비스는 값을 바꾸는 API가 절반이다 |
| 지금처럼 화면마다 직접 | 배경의 둘째 문제가 그대로 남는다 |

## 결과

- 좋아지는 점: 응답이 없으면 15초 뒤 실패로 알린다. 닫힌 화면의 요청이 끊긴다. 서버가 잠깐 답하지 못해도 조회는 스스로 다시 보낸다. 값을 바꾸면 그 값을 보는 모든 화면이 갱신된다.
- 감수하는 점: 의존성이 하나 늘었다(`@tanstack/react-query`). 이 변경 전후로 묶음이 압축 기준 약 501KB에서 약 515KB로 14KB 늘었다. 팀이 이름표와 낡음 표시라는 개념을 알아야 한다. [사용법 문서](../api-module.md)에 예시를 두었다.
- 감수하는 점: 다시 시도가 두 층에 있다. 겹쳐서 여러 번 보내지 않도록 HTTP 클라이언트가 서버 실패(502·503·504)를 맡고, 조회 저장소는 서버에 닿지 못한 경우만 한 번 더 시도한다.
- 감수하는 점: 화면 대부분은 아직 `api`를 직접 부른다. 두 방식이 섞여 있는 동안은 "값을 바꾼 뒤 낡음 표시"를 변경 훅이 아니라 `App.tsx`의 "창을 닫을 때 다시 부르기"가 맡는다. 화면을 옮겨 갈수록 이 장치에 덜 기댄다.
- 감수하는 점: 응답 타입(`types.ts`)은 한 파일에 남겼다. 여러 사람이 동시에 타입을 더하면 같은 파일을 고치게 된다. 불편해지면 분야별로 나눈다.
- 조심할 점: `GET /attempts/current`는 부를 때마다 서버가 자동 제출을 처리한다. 조회처럼 보이지만 결과를 저장해 두면 안 된다. 응시를 맡은 사람이 조회를 만들 때 쓰도록 공통 옵션(`NEVER_CACHE`)을 두고 그 파일에 주석을 남겼다.
- [ADR 0007](0007-no-state-library.md)의 나머지 반쪽("상태 관리 라이브러리를 넣지 않는다")은 그대로다. 로그인 상태는 여전히 React Context 하나다.
